# Паспорт проекта

## Общие сведения

**Название команды:** Кодовые ковырялки  
**Название продукта:** LoyaltyLedger  
**Коды участников:** `M1`, `M2`, `M3`  
**Статус ранней калибровки:** `черновик`

## 1. Назначение

LoyaltyLedger — серверный сервис программы лояльности для интернет-магазина.

Пользователь сможет зарегистрироваться, передавать номера своих заказов, получать бонусные баллы за успешно обработанные заказы и использовать накопленные баллы при оформлении новых заказов.

Собственная предметная логика продукта будет включать проверку и обработку заказов, начисление бонусов, ведение баланса пользователя и выполнение списаний.

## 2. Граница продукта

**В продукт входит:**

- регистрация пользователей;
- вход в систему;
- аутентификация по токену;
- загрузка номеров заказов;
- проверка корректности номера заказа;
- хранение состояния заказов;
- фоновая обработка заказов;
- начисление бонусных баллов;
- просмотр текущего баланса;
- списание бонусных баллов;
- просмотр истории списаний;
- экспорт статистики.

**Внешнее окружение и внешние системы:**

- клиент, отправляющий HTTP-запросы;
- операционная система, в которой запускается сервер;
- файловая система для чтения конфигурации и записи статистики.

**Команда сознательно не реализует:**

- frontend;
- мобильное приложение;
- реальную интеграцию с интернет-магазином;
- реальные платежи;
- интеграцию с банками;
- email- и push-уведомления;
- внешнюю систему начисления бонусов;
- сложную аналитику;
- отдельную промышленную базу данных.

## 3. Пользователи и доступные действия

| Пользователь или роль | Кто это | Что может делать | Что ему недоступно |
| --- | --- | --- | --- |
| Неавторизованный пользователь | Пользователь без действующего токена | Зарегистрироваться, войти в систему | Загружать заказы, смотреть баланс, списывать баллы, получать историю операций |
| Авторизованный пользователь | Зарегистрированный пользователь с действующим токеном | Загружать свои заказы, просматривать свои заказы, смотреть баланс, списывать бонусные баллы, смотреть историю списаний | Получать данные других пользователей, выполнять операции от имени другого пользователя |

## 4. Сквозные сценарии

### Сценарий 1. Регистрация и получение доступа

- **Участники:** неавторизованный пользователь.
- **Начальное условие:** пользователь ещё не зарегистрирован.
- **Основные действия:** пользователь передаёт логин и пароль; система создаёт учётную запись и выдаёт токен.
- **Результат:** пользователь получает возможность обращаться к защищённым операциям.
- **Какие данные или состояние изменяются:** создаётся пользователь и создаётся токен, связанный с его идентификатором.

### Сценарий 2. Загрузка и обработка заказа

- **Участники:** авторизованный пользователь, фоновый процесс обработки заказов.
- **Начальное условие:** пользователь вошёл в систему и имеет номер заказа.
- **Основные действия:** пользователь отправляет номер заказа; система проверяет его и сохраняет; фоновый процесс переводит заказ в обработку и завершает её успешно или отклоняет заказ.
- **Результат:** при успешной обработке пользователь получает бонусные баллы.
- **Какие данные или состояние изменяются:** создаётся заказ, меняется его статус, при успешной обработке увеличивается баланс пользователя.

### Сценарий 3. Списание бонусных баллов

- **Участники:** авторизованный пользователь.
- **Начальное условие:** пользователь имеет достаточный бонусный баланс.
- **Основные действия:** пользователь передаёт номер заказа и сумму списания; система проверяет номер и наличие достаточного баланса.
- **Результат:** бонусные баллы списываются в счёт заказа.
- **Какие данные или состояние изменяются:** уменьшается текущий баланс пользователя и создаётся запись в истории списаний.

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Учётные данные и токены | Пользователь и система | Посторонний может получить доступ к операциям пользователя | Пользователь может потерять доступ, либо другой человек сможет выполнять операции от его имени |
| Заказы | Пользователь и система начислений | Может раскрыться история действий пользователя | Неверное изменение статуса может привести к ошибочному начислению или отсутствию начисления |
| Баланс пользователя | Пользователь | Может раскрыться информация о количестве бонусных баллов | Неверное изменение может привести к лишнему начислению или неправомерному списанию |
| История списаний | Пользователь | Может раскрыться история использования бонусов | Изменение или удаление нарушает корректность истории операций |

## 6. Компоненты и внешние взаимодействия

Предполагаемые компоненты продукта:

- HTTP-сервер;
- слой HTTP-обработчиков;
- слой бизнес-логики;
- in-memory хранилище;
- компонент аутентификации;
- фоновый воркер обработки заказов;
- модуль конфигурации;
- файловая система.

Основные взаимодействия:

- клиент будет отправлять HTTP-запросы серверу;
- HTTP-обработчики будут передавать данные в бизнес-логику;
- бизнес-логика будет обращаться к хранилищу;
- фоновый воркер будет получать необработанные заказы и изменять их состояние;
- компонент аутентификации будет связывать токен с идентификатором пользователя;
- конфигурация будет считываться из файла;
- статистика сможет записываться в файл.

## 7. Откуда продукт получает данные

| Источник | Пример данных | Кто управляет источником | Как продукт использует данные |
| --- | --- | --- | --- |
| HTTP-запрос регистрации | логин, пароль | пользователь | создаёт учётную запись |
| HTTP-запрос входа | логин, пароль | пользователь | проверяет учётные данные и выдаёт токен |
| HTTP-запрос загрузки заказа | номер заказа | пользователь | проверяет и сохраняет заказ |
| HTTP-запрос списания | номер заказа, сумма | пользователь | проверяет возможность списания и изменяет баланс |
| HTTP-заголовок Authorization | токен | пользователь | определяет авторизованного пользователя |
| Файл конфигурации | адрес сервера, порт, параметры фоновой обработки | команда проекта | задаёт параметры запуска приложения |

## 9. Стек и путь к первой работающей версии

**Основные технологии:** Go, стандартная библиотека Go, HTTP, JSON, YAML, in-memory хранилище.

**Технологии, новые для команды:** конкурентная обработка фоновых задач, context, middleware, graceful shutdown.

**Внешние сервисы, необходимые для запуска:** отсутствуют.

**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:**  
Основные сценарии не зависят от внешних сервисов и смогут проверяться локальными HTTP-запросами.

**Что команда реализует первым, чтобы получить запускаемую версию:**  
Минимальный HTTP-сервер с регистрацией пользователя, входом в систему, загрузкой заказа и получением текущего баланса.
