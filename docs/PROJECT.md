# Паспорт проекта

## Общие сведения

**Название команды:** Кодовые ковырялки  
**Название продукта:** LoyaltyLedger  
**Коды участников:** `M1` (Волкова Татьяна), `M2` (Беднова Александра), `M3` (Такаев Денис)  


## 1. Назначение

LoyaltyLedger — серверный сервис программы лояльности для интернет-магазина.

Пользователь сможет зарегистрироваться, передавать номера своих заказов, получать бонусные баллы за успешно обработанные заказы и использовать накопленные баллы при оформлении новых заказов.

Собственная предметная логика продукта будет включать проверку и обработку заказов, начисление бонусов, ведение баланса пользователя и выполнение списаний.

## 2. Граница продукта

**В продукт входит:**

- регистрация пользователей;
- вход в систему;
- аутентификация по токену;
- разграничение прав обычного пользователя и администратора;
- загрузка номеров заказов;
- проверка корректности номера заказа;
- получение информации о заказе из Order Service;
- хранение состояния заказов;
- фоновая обработка заказов;
- начисление бонусных баллов;
- просмотр текущего баланса;
- списание бонусных баллов;
- просмотр истории списаний;
- административный просмотр пользователей и заказов;
- блокировка и разблокировка пользователей;
- экспорт статистики.

**Внешнее окружение и внешние системы:**

- клиент, отправляющий HTTP-запросы;
- Order Service интернет-магазина, который предоставляет информацию о заказе.

**Команда сознательно не реализует:**

- frontend;
- мобильное приложение;
- сам Order Service;
- оформление и доставку заказов;
- реальные платежи и банковские операции;
- email- и push-уведомления;
- сложную аналитику;
- хранение платёжных реквизитов пользователей.

| --- | --- | --- | --- |

## 4. Сквозные сценарии

### Сценарий 1. Регистрация и получение доступа

- **Участники:** неавторизованный пользователь.
- **Начальное условие:** пользователь ещё не зарегистрирован.
- **Основные действия:** пользователь передаёт логин и пароль; система создаёт учётную запись и выдаёт токен.
- **Результат:** пользователь получает доступ к защищённым операциям.
- **Какие данные или состояние изменяются:** создаётся пользователь и токен, связанный с его идентификатором.

### Сценарий 2. Загрузка и обработка заказа

- **Участники:** авторизованный пользователь, LoyaltyLedger, Order Service.
- **Начальное условие:** пользователь вошёл в систему и имеет номер заказа.
- **Основные действия:** пользователь отправляет номер заказа; LoyaltyLedger проверяет его и обращается в Order Service за информацией о заказе; после успешной проверки заказ сохраняется и передаётся в фоновую обработку.
- **Результат:** заказ получает конечный статус, а при успешной обработке пользователю начисляются бонусные баллы.
- **Какие данные или состояние изменяются:** создаётся заказ, меняется его статус, при успешной обработке изменяется баланс пользователя.

### Сценарий 3. Административное управление пользователем

- **Участники:** администратор.
- **Начальное условие:** администратор авторизован, пользователь существует в системе.
- **Основные действия:** администратор находит пользователя, просматривает его состояние и при необходимости блокирует или разблокирует его.
- **Результат:** изменяется возможность пользователя выполнять защищённые операции.
- **Какие данные или состояние изменяются:** изменяется статус учётной записи пользователя.

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |

## 6. Компоненты и внешние взаимодействия

Предполагаемые компоненты продукта:

- HTTP-сервер;
- слой HTTP-обработчиков;
- middleware аутентификации и проверки прав;
- слой бизнес-логики;
- компонент доступа к данным;
- PostgreSQL;
- компонент аутентификации;
- фоновый воркер обработки заказов;
- административные операции;
- модуль конфигурации;
- модуль экспорта статистики.

Инфраструктурные компоненты:

- Docker;
- Docker Compose для локального запуска приложения и PostgreSQL.

Внешняя система:

- Order Service интернет-магазина.

Основные взаимодействия:

- клиент отправляет HTTP-запросы серверу;
- HTTP-слой проверяет аутентификацию и передаёт данные в бизнес-логику;
- бизнес-логика обращается к PostgreSQL через слой доступа к данным;
- PostgreSQL хранит пользователей, заказы, балансы и историю операций;
- при загрузке заказа LoyaltyLedger обращается в Order Service и получает информацию о заказе;
- фоновый воркер получает необработанные заказы и изменяет их состояние;
- административные операции проверяют наличие соответствующих прав;
- конфигурация задаёт параметры HTTP-сервера, базы данных и фоновой обработки;
- экспорт статистики формирует файл с агрегированной информацией.

## 7. Откуда продукт получает данные

| Источник | Пример данных | Кто управляет источником | Как продукт использует данные |
| --- | --- | --- | --- |
| HTTP-запрос регистрации | логин, пароль | пользователь | создаёт учётную запись |
| HTTP-запрос входа | логин, пароль | пользователь | проверяет учётные данные и выдаёт токен |
| HTTP-запрос загрузки заказа | номер заказа | пользователь | запускает проверку и обработку заказа |
| HTTP-запрос списания | номер заказа, сумма | пользователь | проверяет возможность списания и изменяет баланс |
| HTTP-заголовок Authorization | токен | пользователь | определяет авторизованного пользователя |
| Административный HTTP-запрос | идентификатор пользователя, действие | администратор | получает административные данные или изменяет статус пользователя |
| Order Service | идентификатор заказа, его состояние, информация о владельце | интернет-магазин | позволяет проверить существование и состояние заказа |
| Файл или переменные конфигурации | адрес сервера, параметры PostgreSQL, интервалы обработки | команда проекта | задают параметры запуска приложения |

## 9. Стек и путь к первой работающей версии

**Основные технологии:** Go, HTTP, JSON, PostgreSQL, SQL, Docker, Docker Compose.

**Технологии, новые для команды:** работа с PostgreSQL из серверного приложения, контейнеризация через Docker, конкурентная обработка фоновых задач, context, middleware и graceful shutdown.

**Внешние сервисы, необходимые для запуска:** Order Service.

**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:**  
При недоступности реального Order Service команда будет использовать тестовую или локальную реализацию с заранее подготовленными ответами, чтобы основные сценарии проекта можно было проверять локально.

**Что команда реализует первым, чтобы получить запускаемую версию:**  
Минимальный HTTP-сервер, подключение к PostgreSQL и базовые операции регистрации и входа пользователя.
