# Модель угроз LoyaltyLedger

## 1. Цель модели угроз

Цель модели угроз — определить наиболее существенные сценарии нарушения безопасности LoyaltyLedger и связать их с требованиями безопасности `SR-*`.

Основное внимание уделяется угрозам, которые могут привести к:

- несанкционированному доступу к данным пользователей;
- краже или неправильному использованию бонусных баллов;
- повторному начислению бонусов;
- обходу разграничения ролей;
- нарушению целостности заказов и финансовых операций;
- использованию недостоверных данных внешнего Order Service;
- компрометации учётных данных и пользовательских сессий.

# 3. Границы доверия

## TB-01. Клиент → LoyaltyLedger API

Клиентская сторона находится за пределами доверенной зоны приложения.

Система не должна доверять:

- содержимому HTTP-запросов;
- значениям идентификаторов;
- переданным номерам заказов;
- суммам списания;
- заявленной роли пользователя;
- bearer-токену до его проверки;
- размеру и формату запроса.

Любые данные от клиента считаются потенциально контролируемыми атакующим.

---

## TB-02. LoyaltyLedger → Order Service

Order Service является внешней системой.

Даже если сервис считается легитимным, LoyaltyLedger не должен безусловно доверять полученному ответу.

Необходимо учитывать:

- недоступность сервиса;
- таймауты;
- некорректный формат ответа;
- несоответствие номера заказа;
- неправильного владельца;
- неожиданное состояние заказа;
- некорректную сумму заказа.

Финансовое состояние LoyaltyLedger не должно изменяться, если данные Order Service не удалось достоверно проверить.

---

## TB-03. LoyaltyLedger → PostgreSQL

База данных является доверенным хранилищем состояния, однако необходимо учитывать последствия её возможной компрометации.

В частности, утечка базы не должна непосредственно раскрывать:

- исходные пароли пользователей;
- действующие bearer-токены.

Кроме того, ограничения целостности должны применяться не только на уровне приложения, но и, где это возможно, на уровне БД.

---

## TB-04. Background workers → общее состояние системы

Фоновые обработчики работают с теми же заказами и балансами, что и HTTP-запросы.

Следовательно, необходимо учитывать конкурентное выполнение:

- нескольких воркеров;
- воркера и пользовательского запроса;
- повторной обработки одного заказа.

Фоновые операции не должны приводить к двойному начислению или нарушению целостности баланса.

---

# 4. Защищаемые активы

Основными активами LoyaltyLedger являются:

### A-01. Учётные данные пользователей

Логины и пароли, используемые для аутентификации.

### A-02. Сессионные токены

Bearer-токены, предоставляющие доступ к защищённым методам API.

### A-03. Баланс бонусов

Текущее количество бонусных баллов пользователя.

Нарушение целостности этого значения напрямую влияет на финансовую логику приложения.

### A-04. Информация о заказах

Номер заказа, владелец, состояние, сумма и информация о начисленных бонусах.

### A-05. История списаний

Записи об использовании бонусных баллов пользователями.

### A-06. Административные функции

Возможности просмотра пользователей и заказов, блокировки аккаунтов и получения статистики.

# 5. Угрозы

## T-01. Компрометация учётных данных пользователя

**Сценарий.**

Атакующий получает доступ к базе данных или другому хранилищу и пытается восстановить исходные пароли пользователей.

Особенно критичным является случай, если пароль хранится в открытом виде или с использованием обратимого преобразования.

**Последствия.**

Атакующий может:

- получить доступ к аккаунту пользователя;
- узнать его баланс и историю;
- списать накопленные бонусы;
- использовать тот же пароль на других сервисах, если пользователь повторно использует пароль.

**Связанные активы:** `A-01`, `A-03`.

**Связанные требования:** `SR-01`.

**Приоритет:** высокий.

---

## T-02. Кража или подделка пользовательской сессии

**Сценарий.**

Атакующий получает bearer-токен пользователя либо пытается подобрать или самостоятельно сформировать действующий токен.

Возможен также сценарий компрометации базы данных, если сессионные токены хранятся в ней в исходном виде.

**Последствия.**

Атакующий получает доступ к API от имени другого пользователя без знания его пароля.

Это может привести к:

- просмотру пользовательских данных;
- просмотру заказов;
- списанию бонусов;
- другим действиям от имени владельца аккаунта.

**Связанные активы:** `A-02`, `A-03`, `A-04`, `A-05`.

**Связанные требования:** `SR-02`.

**Приоритет:** высокий.

---

## T-03. Получение доступа к данным другого пользователя

**Сценарий.**

Атакующий, имеющий легитимный пользовательский аккаунт, изменяет параметры HTTP-запроса или идентификаторы ресурсов с целью получить данные другого пользователя.

Например, атакующий может попытаться:

- передать чужой `user_id`;
- запросить чужой заказ;
- получить чужой баланс;
- получить историю чужих списаний;
- использовать чужой номер заказа.

Это является классическим сценарием нарушения объектного уровня авторизации.

**Последствия.**

Возможны:

- утечка персональных и финансовых данных;
- операции с чужими заказами;
- использование чужих бонусов;
- нарушение изоляции пользователей.

**Связанные активы:** `A-03`, `A-04`, `A-05`.

**Связанные требования:** `SR-03`.

**Приоритет:** критический.

---

## T-04. Обход разграничения ролей

**Сценарий.**

Обычный пользователь пытается вызвать административные методы API напрямую.

Например:

```text
/api/admin/users
/api/admin/orders
/api/admin/stats
/api/admin/users/{id}/block
```

Атакующий может игнорировать отсутствие соответствующих кнопок в пользовательском интерфейсе и отправлять HTTP-запросы непосредственно.

Поэтому разграничение доступа только на уровне клиентского интерфейса недостаточно.

**Последствия.**

Обычный пользователь может получить возможность:

- просматривать всех пользователей;
- просматривать чужие заказы;
- получать административную статистику;
- блокировать других пользователей;
- выполнять иные административные операции.

**Связанные активы:** `A-04`, `A-06`.

**Связанные требования:** `SR-04`.

**Приоритет:** критический.

---

## T-05. Использование заблокированного аккаунта

**Сценарий.**

Администратор блокирует пользователя, однако ранее выданный пользовательский токен продолжает оставаться действительным.

В другом варианте заблокированный пользователь продолжает успешно выполнять новый вход.

Фоновая обработка также может продолжить начислять бонусы такому пользователю.

**Последствия.**

Блокировка фактически не выполняет свою функцию.

Пользователь продолжает:

- обращаться к API;
- использовать старую сессию;
- выполнять операции;
- потенциально получать начисления.

**Связанные активы:** `A-02`, `A-03`, `A-04`.

**Связанные требования:** `SR-05`.

**Приоритет:** средний.

---

## T-06. Повторное начисление бонусов за один заказ

**Сценарий.**

Пользователь несколько раз отправляет один и тот же номер заказа либо один заказ одновременно обрабатывается несколькими фоновыми воркерами.

Возможны следующие варианты:

- повторный POST одного заказа;
- повторная постановка заказа в обработку;
- конкурентная обработка двумя воркерами;
- повторный запуск обработки после частично завершённой операции.

Если операция не является идемпотентной, один заказ может несколько раз увеличить пользовательский баланс.

**Последствия.**

Пользователь искусственно получает дополнительные бонусы.

Это приводит к прямому нарушению финансовой целостности программы лояльности.

**Связанные активы:** `A-03`, `A-04`.

**Связанные требования:** `SR-06`.

**Приоритет:** критический.

---

## T-07. Двойное или некорректное списание бонусов

**Сценарий.**

Пользователь отправляет несколько запросов списания одновременно.

Например, пользователь имеет баланс:

```text
100 баллов
```

и одновременно отправляет два запроса:

```text
списать 80
списать 80
```

Если оба запроса независимо проверят старое значение баланса до его обновления, оба могут быть приняты.

Отдельный пограничный случай - два одновременных одинаковых запроса на списание одного заказа. Оба запроса могут пройти предварительную проверку отсутствия списания, если эта проверка выполняется до транзакции. Без повторной проверки внутри сериализованной транзакции система может дважды уменьшить баланс, хотя клиент отправил одну и ту же операцию повторно.

Также возможны:

- повтор одного и того же запроса, в том числе параллельный;
- списание на уже обработанный заказ;
- списание суммы больше стоимости заказа;
- попытка списания с чужого заказа.

**Последствия.**

Возможны:

- отрицательный баланс;
- двойное расходование одних и тех же бонусов;
- некорректная история операций;
- финансовые потери.

**Связанные активы:** `A-03`, `A-04`, `A-05`.

**Связанные требования:** `SR-03`, `SR-07`.

**Приоритет:** критический.

---

## T-08. Использование поддельных или некорректных данных Order Service

**Сценарий.**

LoyaltyLedger получает от внешнего Order Service некорректные либо неожиданные данные.

Например:

- заказ принадлежит другому пользователю;
- номер заказа в ответе отличается от запрошенного;
- сумма заказа отрицательная;
- состояние заказа неизвестно;
- JSON имеет некорректный формат;
- сервис вернул неполный ответ;
- сервис недоступен или превысил допустимое время ответа.

Если LoyaltyLedger автоматически доверяет этим данным, они могут привести к некорректному начислению или списанию.

**Последствия.**

Возможны:

- начисление за чужой заказ;
- начисление неправильной суммы;
- списание на недопустимый заказ;
- нарушение целостности баланса.

**Связанные активы:** `A-03`, `A-04`.

**Связанные требования:** `SR-03`, `SR-08`.

**Приоритет:** высокий.

---

## T-09. Некорректные или чрезмерно большие входные данные

**Сценарий.**

Атакующий отправляет специально сформированные запросы:

- чрезмерно большой JSON;
- некорректный JSON;
- отрицательные финансовые значения;
- очень длинные строки;
- неизвестные поля;
- некорректные параметры пагинации;
- несколько JSON-объектов вместо одного.

Целью может быть нарушение бизнес-логики или создание избыточной нагрузки на сервер.

**Последствия.**

Возможны:

- повреждение данных;
- ошибки бизнес-логики;
- чрезмерное потребление памяти;
- деградация производительности;
- отказ сервиса.

**Связанные активы:** `A-03`, `A-04`, доступность системы.

**Связанные требования:** `SR-09`.

**Приоритет:** средний.

# 6. Приоритетные угрозы

Для EK1 в качестве наиболее существенных угроз выделены следующие:

| ID | Угроза | Приоритет | Причина |
|---|---|---|---|
| `T-03` | Доступ к данным другого пользователя | Критический | Нарушает изоляцию пользователей и позволяет работать с чужими данными |
| `T-04` | Обход разграничения ролей | Критический | Может предоставить обычному пользователю административные полномочия |
| `T-06` | Повторное начисление бонусов | Критический | Позволяет напрямую искусственно увеличить баланс |
| `T-07` | Двойное/некорректное списание | Критический | Нарушает финансовую целостность и может привести к double spending |
| `T-02` | Компрометация сессии | Высокий | Позволяет полностью действовать от имени другого пользователя |

Именно для этих угроз должны быть наиболее явно описаны проектные решения `D-*` и способы проверки.

# 8. Пример основной цепочки угрозы

Одна из ключевых цепочек безопасности проекта выглядит следующим образом:

```text
T-07
Двойное или конкурентное списание бонусов
        │
        ▼
SR-07
Списание должно быть атомарным,
баланс не должен становиться отрицательным
        │
        ▼
D-*
Атомарное условное обновление баланса
в транзакции базы данных
        │
        ▼
Проверка
Два параллельных запроса пытаются списать
средства, которых достаточно только для одного
        │
        ▼
Ожидаемый результат
Успешен максимум один запрос,
итоговый баланс >= 0
```

Аналогичные связи должны существовать для остальных приоритетных угроз.
