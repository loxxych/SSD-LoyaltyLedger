# Проектные решения безопасности

Для LoyaltyLedger выделены три основных проектных решения безопасности. Каждое решение связано с требованиями `SR-*`, угрозами `T-*` и способом последующей проверки.

---

# D-01. Безопасная аутентификация и разграничение доступа

## Решаемая проблема

Необходимо защитить учётные записи пользователей, пользовательские сессии и административные функции системы.

Решение направлено против:

- компрометации паролей;
- кражи или подделки сессий;
- доступа к данным другого пользователя;
- обхода разграничения ролей;
- использования заблокированного аккаунта.

## Решение

Пароли пользователей не хранятся в открытом виде. Для их хранения используется `bcrypt`.

После успешной аутентификации система создаёт криптографически случайный bearer-токен. В базе данных сохраняется не исходный токен, а его SHA-256-хеш.

При каждом защищённом запросе LoyaltyLedger:

1. проверяет переданный токен;
2. определяет соответствующего пользователя;
3. проверяет состояние его аккаунта;
4. проверяет роль пользователя;
5. только после этого передаёт запрос соответствующему обработчику.

```text
HTTP request
     │
     v
Bearer token
     │
     v
Authentication
     │
     v
User + account state
     │
     v
Role check
     │
     ├── access denied
     │
     v
Business operation
```

Обычный пользователь не может обращаться к административным маршрутам.

Пользовательские операции выполняются от имени пользователя, определённого по сессии, а не по переданному клиентом `user_id`.

При блокировке пользователя его существующие сессии инвалидируются.

## Обоснование

Проверка доступа должна выполняться на стороне сервера, поскольку клиент может самостоятельно сформировать произвольный HTTP-запрос.

Хранение паролей и токенов в открытом виде также создаёт дополнительный риск при компрометации базы данных.

Объединение аутентификации, серверной проверки ролей и контроля состояния аккаунта обеспечивает единый механизм управления доступом.

## Связи

**Угрозы:** `T-01`, `T-02`, `T-03`, `T-04`, `T-05`.

**Требования:** `SR-01`, `SR-02`, `SR-03`, `SR-04`, `SR-05`.

## Ограничения

Решение не защищает исходный bearer-токен после его компрометации на стороне клиента.

При реальном развёртывании системы требуется HTTPS, а токены не должны попадать в журналы приложения.

Также важно, чтобы каждый административный маршрут действительно использовал проверку роли.

## Проверки: реализованные и планируемые

В коде уже есть автоматические проверки (их выполнение зависит от доступности PostgreSQL для интеграционных тестов):

- `TestRegistrationAndLogin` (`internal/service/service_test.go`) проверяет регистрацию, хеширование пароля, вход с верным и неверным паролем и запрет входа заблокированному пользователю;
- `TestTokens` (`internal/auth/auth_test.go`) проверяет создание и проверку токенов;
- `TestRoleBoundary` (`internal/middleware/middleware_test.go`) проверяет разграничение административного доступа;
- `TestHTTPScenariosWithPostgres` (`internal/store/store_test.go`) проверяет сценарии API с PostgreSQL.

Дополнительно перед защитой следует проверить:

- пароль отсутствует в БД в открытом виде;
- вход с правильным паролем успешен;
- вход с неправильным паролем отклоняется;
- два входа создают разные токены;
- исходный токен отсутствует в БД;
- запрос без токена отклоняется;
- изменённый токен отклоняется;
- обычный пользователь не имеет доступа к `/api/admin/*`;
- пользователь не может получить данные другого пользователя;
- после блокировки старый токен перестаёт работать;
- заблокированный пользователь не может выполнить новый вход.

# D-02. Транзакционная и идемпотентная обработка бонусных операций

## Решаемая проблема

Основные финансовые операции LoyaltyLedger не должны приводить к:

- повторному начислению бонусов за один заказ;
- повторному списанию;
- отрицательному балансу;
- использованию одного баланса несколькими конкурентными запросами.

Решение направлено прежде всего против `T-06` и `T-07`.

## Решение

Операции начисления и списания выполняются с использованием транзакций PostgreSQL и ограничений целостности базы данных.

Номер заказа используется как уникальный идентификатор, что предотвращает создание нескольких независимых записей для одного заказа.

Повторная обработка уже завершённого заказа не должна повторно начислять бонусы.

При списании проверка доступного баланса и его изменение выполняются атомарно.

Концептуально операция выглядит следующим образом:

```sql
UPDATE balances
SET current = current - :amount,
    withdrawn = withdrawn + :amount
WHERE user_id = :user_id
  AND current >= :amount;
```

Если средств недостаточно, обновление не выполняется. Изменение баланса и запись о списании выполняются в одной транзакции.

Связанные изменения состояния выполняются внутри транзакции.

```text
Order / withdrawal request
          │
          v
 Validate operation
          │
          v
 Begin transaction
          │
          v
Atomic database changes
          │
          ├── error -> rollback
          │
          v
        commit
```

## Обоснование

Проверки только на уровне Go-кода недостаточно при конкурентном выполнении запросов.

Например:

```text
balance = 100

Request A reads 100
Request B reads 100

A wants to spend 80
B wants to spend 80
```

Если проверка и изменение баланса выполняются отдельно, оба запроса могут решить, что средств достаточно.

Атомарное условие в `UPDATE` не позволяет двум разным списаниям потратить один и тот же остаток. Ограничения уникальности также защищают систему от повторной обработки одного заказа несколькими воркерами или повторными HTTP-запросами.

### Контрпример: одновременный повтор одного списания

Первоначально можно предположить, что предварительной проверки существующего списания достаточно для идемпотентности. Но два одинаковых запроса для одного заказа могут одновременно проверить, что записи ещё нет, и оба перейти к списанию. Если после этого просто обновить баланс, не выполнив повторную проверку в транзакции, баланс уменьшится дважды.

Это затрагивает `T-07` и `SR-07`: повтор одной операции не должен повторно расходовать бонусы. Поэтому `D-02` опирается не только на предварительную проверку в сервисе: транзакция блокирует строку пользователя, повторно проверяет существующее списание, условно изменяет баланс, а затем записывает списание. Уникальность номера заказа в БД служит дополнительной защитой; ошибка записи откатывает изменение баланса.

Сценарий одновременного повтора уже покрыт интеграционным тестом `TestPostgresDebitIdempotenceAndRollback` (`internal/store/store_test.go`): десять одинаковых конкурентных запросов по одному номеру заказа дают одно списание; другой размер для этого заказа конфликтует, а ошибка вставки истории откатывает изменение баланса. Тесты `TestPostgresConcurrentDebits` и `TestPostgresAccrualOnceAndPersistence` покрывают конкурентные разные списания и повторные начисления. Их наличие в коде не означает, что они запускались на текущей машине: интеграционные тесты пропускаются без `TEST_DATABASE_URL`.

### Сравнение способов обеспечить достаточность баланса

**Выбранный способ - условный `UPDATE` в БД.** База атомарно проверяет `current >= amount` и уменьшает баланс одним оператором. Это короткий путь, при котором проверяемое условие находится рядом с изменением. Он подходит, пока все списания используют одну строку баланса в PostgreSQL и совершаются через эту транзакционную логику.

**Альтернатива - `SELECT ... FOR UPDATE`, проверка в Go и последующий `UPDATE`.** Она также может быть корректной, если блокировка удерживается до конца транзакции и каждый путь изменения баланса соблюдает тот же порядок. Она позволяет выполнить дополнительные ветвления по прочитанному состоянию, но требует нескольких операций и повышает риск пропустить блокировку или проверку в новом пути кода.

Мы выбираем условный `UPDATE`, сохраняя транзакцию для атомарности баланса и истории. Если баланс будет распределён по нескольким строкам или хранилищам, появятся резервы либо часть списаний начнёт обходить этот путь, решение нужно пересмотреть. План проверки учитывает и параллельные разные списания, и параллельный повтор одного заказа, и откат транзакции при ошибке записи истории.

## Связи

**Угрозы:** `T-06`, `T-07`.

**Требования:** `SR-06`, `SR-07`.

## Ограничения

Транзакция базы данных защищает только локальное состояние LoyaltyLedger.

Она не может сделать одной транзакцией действия LoyaltyLedger и внешнего Order Service.

Поэтому информация внешней системы должна быть проверена до изменения финансового состояния.

## Проверки: реализованные и планируемые

Уже есть автоматические тесты:

- `TestPostgresAccrualOnceAndPersistence` (`internal/store/store_test.go`) параллельно обрабатывает один заказ и проверяет единственное начисление и сохранение данных;
- `TestPostgresConcurrentDebits` проверяет конкурентные списания с разными номерами заказов и достаточность общего баланса;
- `TestPostgresDebitIdempotenceAndRollback` проверяет конкурентные повторы одного списания, конфликт другой суммы и откат при ошибке записи истории.

Интеграционные тесты требуют PostgreSQL и `TEST_DATABASE_URL`; перед защитой следует запустить их в настроенном окружении и зафиксировать результат.

Дополнительный ручной сценарий для начисления:

1. загрузить один заказ;
2. обработать его;
3. повторно отправить тот же номер;
4. повторно запустить обработку;
5. выполнить несколько параллельных обработок.

Ожидаемый результат — бонусы начисляются ровно один раз.

Для списания:

```text
Начальный баланс = 100

Request A: withdraw 80, order 1
Request B: withdraw 80, order 2
```

Это разные номера заказов; запросы выполняются одновременно. Для двух одинаковых запросов на один заказ допустимы два успешных ответа, но история должна содержать одно списание, а баланс уменьшиться один раз.

Ожидаемый результат:

- успешно не более одного запроса;
- итоговый баланс неотрицательный;
- история содержит только реально выполненное списание.

Также проверяются два одновременных одинаковых запроса на один заказ и повтор того же заказа с другой суммой. Первый случай должен дать только одно уменьшение баланса и одну запись; второй должен завершиться конфликтом без изменения баланса. Ошибка записи истории после изменения баланса должна откатывать всю транзакцию.

# D-03. Проверка недоверенных входных и внешних данных

## Решаемая проблема

LoyaltyLedger получает данные из двух недоверенных источников:

1. HTTP-запросы пользователей;
2. внешний Order Service.

Некорректные или специально сформированные данные не должны приводить к ошибочным начислениям, списаниям или нарушению работы системы.

## Решение

Любые данные клиента проходят проверку до выполнения бизнес-операции.

Проверяются:

- формат и длина логина;
- пароль;
- формат номера заказа;
- сумма списания;
- параметры пагинации;
- структура JSON;
- размер HTTP-запроса.

Ответ внешнего Order Service также не считается автоматически доверенным.

Перед выполнением финансовой операции проверяются:

- номер заказа;
- владелец заказа;
- состояние заказа;
- сумма заказа;
- корректность структуры ответа.

Также обрабатываются:

- сетевые ошибки;
- HTTP-ошибки;
- таймауты;
- некорректный JSON;
- чрезмерно большие ответы.

```text
Client / Order Service
          │
          v
     Untrusted data
          │
          v
       Validation
          │
     ┌────┴────┐
 invalid     valid
    │           │
 reject         v
           Business logic
```

Если данные нельзя корректно проверить, финансовая операция не выполняется.

## Обоснование

Нельзя полагаться на валидацию только клиентского интерфейса, поскольку пользователь может отправить HTTP-запрос напрямую.

Order Service также находится за отдельной границей доверия: даже успешный HTTP-ответ не гарантирует корректность содержащихся в нём бизнес-данных.

Поскольку эти данные влияют на баланс пользователя, их необходимо проверять непосредственно в LoyaltyLedger.

## Связи

**Угрозы:** `T-03`, `T-08`, `T-09`.

**Требования:** `SR-03`, `SR-08`, `SR-09`.

## Ограничения

Ограничение размера одного запроса не является полноценной защитой от распределённой DoS-атаки.

В production-среде могут дополнительно потребоваться:

- HTTPS;
- rate limiting;
- reverse proxy;
- межсервисная аутентификация.

## Проверки: реализованные и планируемые

Уже есть автоматические тесты:

- `TestCreateOrderTrustBoundary` и `TestCreateOrderDuplicateWithoutRemote` (`internal/service/service_test.go`) проверяют владельца, состояние, формат заказа и отказ до обращения к внешнему сервису для некорректного/повторного номера;
- `TestWithdrawalValidation` проверяет сумму, владельца и допустимое состояние заказа;
- `TestWorkerUsesRealState` проверяет обработку корректных, недоступных и некорректных ответов Order Service;
- `TestClientContract` и `TestClientTimeout` (`internal/orders/client_test.go`) проверяют формат/содержимое ответов, HTTP-ошибки и таймаут.

Отдельного теста для всех перечисленных ограничений размера входного и внешнего тела ответа в списке выше нет; эти случаи остаются планом проверки.

Дополнительный ручной сценарий для пользовательского API:

- некорректный JSON;
- отсутствующие обязательные поля;
- отрицательная сумма;
- нулевая сумма;
- неправильный номер заказа;
- слишком большое тело запроса;
- некорректные параметры пагинации.

Система должна отклонить запрос без изменения данных.

Для Order Service тестовый stub последовательно возвращает:

- заказ другого пользователя;
- другой номер заказа;
- отрицательную сумму;
- неизвестное состояние;
- повреждённый JSON;
- HTTP 500;
- таймаут.

Во всех таких случаях баланс пользователя не должен изменяться.
