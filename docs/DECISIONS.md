# Проектные решения безопасности

Для LoyaltyLedger выделены три основных проектных решения безопасности. Каждое решение связано с требованиями `SR-*`, угрозами `T-*` и способом последующей проверки.

---

# D-01. Безопасная аутентификация и разграничение доступа

## Решаемая проблема

Необходимо защитить учётные записи пользователей, пользовательские сессии и административные функции системы.

Решение направлено против:

- компрометации паролей;
- кражи или подделки сессий;
- доступа к данным другого пользователя;
- обхода разграничения ролей;
- использования заблокированного аккаунта.

## Решение

Пароли пользователей не хранятся в открытом виде. Для их хранения используется `bcrypt`.

После успешной аутентификации система создаёт криптографически случайный bearer-токен. В базе данных сохраняется не исходный токен, а его SHA-256-хеш.

При каждом защищённом запросе LoyaltyLedger:

1. проверяет переданный токен;
2. определяет соответствующего пользователя;
3. проверяет состояние его аккаунта;
4. проверяет роль пользователя;
5. только после этого передаёт запрос соответствующему обработчику.

```text
HTTP request
     │
     ▼
Bearer token
     │
     ▼
Authentication
     │
     ▼
User + account state
     │
     ▼
Role check
     │
     ├── access denied
     │
     ▼
Business operation
```

Обычный пользователь не может обращаться к административным маршрутам.

Пользовательские операции выполняются от имени пользователя, определённого по сессии, а не по переданному клиентом `user_id`.

При блокировке пользователя его существующие сессии инвалидируются.

## Обоснование

Проверка доступа должна выполняться на стороне сервера, поскольку клиент может самостоятельно сформировать произвольный HTTP-запрос.

Хранение паролей и токенов в открытом виде также создаёт дополнительный риск при компрометации базы данных.

Объединение аутентификации, серверной проверки ролей и контроля состояния аккаунта обеспечивает единый механизм управления доступом.

## Связи

**Угрозы:** `T-01`, `T-02`, `T-03`, `T-04`, `T-05`.

**Требования:** `SR-01`, `SR-02`, `SR-03`, `SR-04`, `SR-05`.

## Ограничения

Решение не защищает исходный bearer-токен после его компрометации на стороне клиента.

При реальном развёртывании системы требуется HTTPS, а токены не должны попадать в журналы приложения.

Также важно, чтобы каждый административный маршрут действительно использовал проверку роли.

## Будущая проверка

Необходимо проверить:

- пароль отсутствует в БД в открытом виде;
- вход с правильным паролем успешен;
- вход с неправильным паролем отклоняется;
- два входа создают разные токены;
- исходный токен отсутствует в БД;
- запрос без токена отклоняется;
- изменённый токен отклоняется;
- обычный пользователь не имеет доступа к `/api/admin/*`;
- пользователь не может получить данные другого пользователя;
- после блокировки старый токен перестаёт работать;
- заблокированный пользователь не может выполнить новый вход.

# D-02. Транзакционная и идемпотентная обработка бонусных операций

## Решаемая проблема

Основные финансовые операции LoyaltyLedger не должны приводить к:

- повторному начислению бонусов за один заказ;
- повторному списанию;
- отрицательному балансу;
- использованию одного баланса несколькими конкурентными запросами.

Решение направлено прежде всего против `T-06` и `T-07`.

## Решение

Операции начисления и списания выполняются с использованием транзакций PostgreSQL и ограничений целостности базы данных.

Номер заказа используется как уникальный идентификатор, что предотвращает создание нескольких независимых записей для одного заказа.

Повторная обработка уже завершённого заказа не должна повторно начислять бонусы.

При списании проверка доступного баланса и его изменение выполняются атомарно.

Концептуально операция выглядит следующим образом:

```sql
UPDATE users
SET balance = balance - :amount
WHERE id = :user_id
  AND balance >= :amount;
```

Если средств недостаточно, обновление не выполняется.

Связанные изменения состояния выполняются внутри транзакции.

```text
Order / withdrawal request
          │
          ▼
 Validate operation
          │
          ▼
 Begin transaction
          │
          ▼
Atomic database changes
          │
          ├── error → rollback
          │
          ▼
        commit
```

## Обоснование

Проверки только на уровне Go-кода недостаточно при конкурентном выполнении запросов.

Например:

```text
balance = 100

Request A reads 100
Request B reads 100

A wants to spend 80
B wants to spend 80
```

Если проверка и изменение баланса выполняются отдельно, оба запроса могут решить, что средств достаточно.

Атомарные операции PostgreSQL предотвращают такую ситуацию.

Ограничения уникальности также защищают систему от повторной обработки одного заказа несколькими воркерами или повторными HTTP-запросами.

## Связи

**Угрозы:** `T-06`, `T-07`.

**Требования:** `SR-06`, `SR-07`.

## Ограничения

Транзакция базы данных защищает только локальное состояние LoyaltyLedger.

Она не может сделать одной транзакцией действия LoyaltyLedger и внешнего Order Service.

Поэтому информация внешней системы должна быть проверена до изменения финансового состояния.

## Будущая проверка

Для начисления:

1. загрузить один заказ;
2. обработать его;
3. повторно отправить тот же номер;
4. повторно запустить обработку;
5. выполнить несколько параллельных обработок.

Ожидаемый результат — бонусы начисляются ровно один раз.

Для списания:

```text
Начальный баланс = 100

Request A: withdraw 80
Request B: withdraw 80
```

Запросы выполняются одновременно.

Ожидаемый результат:

- успешно не более одного запроса;
- итоговый баланс неотрицательный;
- история содержит только реально выполненное списание.

Также проверяется повтор одного и того же запроса на списание — повторная операция не должна повторно уменьшать баланс.

# D-03. Проверка недоверенных входных и внешних данных

## Решаемая проблема

LoyaltyLedger получает данные из двух недоверенных источников:

1. HTTP-запросы пользователей;
2. внешний Order Service.

Некорректные или специально сформированные данные не должны приводить к ошибочным начислениям, списаниям или нарушению работы системы.

## Решение

Любые данные клиента проходят проверку до выполнения бизнес-операции.

Проверяются:

- формат и длина логина;
- пароль;
- формат номера заказа;
- сумма списания;
- параметры пагинации;
- структура JSON;
- размер HTTP-запроса.

Ответ внешнего Order Service также не считается автоматически доверенным.

Перед выполнением финансовой операции проверяются:

- номер заказа;
- владелец заказа;
- состояние заказа;
- сумма заказа;
- корректность структуры ответа.

Также обрабатываются:

- сетевые ошибки;
- HTTP-ошибки;
- таймауты;
- некорректный JSON;
- чрезмерно большие ответы.

```text
Client / Order Service
          │
          ▼
     Untrusted data
          │
          ▼
       Validation
          │
     ┌────┴────┐
 invalid     valid
    │           │
 reject         ▼
           Business logic
```

Если данные нельзя корректно проверить, финансовая операция не выполняется.

## Обоснование

Нельзя полагаться на валидацию только клиентского интерфейса, поскольку пользователь может отправить HTTP-запрос напрямую.

Order Service также находится за отдельной границей доверия: даже успешный HTTP-ответ не гарантирует корректность содержащихся в нём бизнес-данных.

Поскольку эти данные влияют на баланс пользователя, их необходимо проверять непосредственно в LoyaltyLedger.

## Связи

**Угрозы:** `T-03`, `T-08`, `T-09`.

**Требования:** `SR-03`, `SR-08`, `SR-09`.

## Ограничения

Ограничение размера одного запроса не является полноценной защитой от распределённой DoS-атаки.

В production-среде могут дополнительно потребоваться:

- HTTPS;
- rate limiting;
- reverse proxy;
- межсервисная аутентификация.

## Будущая проверка

Для пользовательского API отправляются:

- некорректный JSON;
- отсутствующие обязательные поля;
- отрицательная сумма;
- нулевая сумма;
- неправильный номер заказа;
- слишком большое тело запроса;
- некорректные параметры пагинации.

Система должна отклонить запрос без изменения данных.

Для Order Service тестовый stub последовательно возвращает:

- заказ другого пользователя;
- другой номер заказа;
- отрицательную сумму;
- неизвестное состояние;
- повреждённый JSON;
- HTTP 500;
- таймаут.

Во всех таких случаях баланс пользователя не должен изменяться.
