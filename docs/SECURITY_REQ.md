# Требования безопасности

В данном разделе определены требования безопасности для LoyaltyLedger. Идентификаторы `SR-*` являются стабильными и далее используются для связи требований с угрозами `T-*`, проектными решениями `D-*` и проверками.

## SR-01. Защита учётных данных

**Требование.**  
Система не должна хранить пароли пользователей и администратора в открытом виде. Компрометация базы данных не должна непосредственно раскрывать исходные пароли.

Пароль не должен возвращаться через API или попадать в данные профиля пользователя.

**Критерий приёмки.**

После регистрации пользователя:

- в таблице пользователей отсутствует исходный пароль;
- сохранённое значение отличается от исходного пароля и представляет собой одностороннее криптографическое представление;
- вход с правильным паролем выполняется успешно;
- вход с неправильным паролем отклоняется;
- API профиля и административные методы не возвращают пароль или его хеш.

---

## SR-02. Безопасная аутентификация и управление сессиями

**Требование.**  
Доступ к защищённым методам API должен предоставляться только после успешной аутентификации.

Сессионный токен должен быть непредсказуемым, иметь ограниченный срок действия и не должен храниться в базе данных в исходном виде.

Отсутствующий, некорректный, неизвестный или просроченный токен не должен предоставлять доступ к защищённым ресурсам.

**Критерий приёмки.**

Проверяются следующие случаи:

1. запрос к защищённому endpoint без токена отклоняется;
2. запрос со случайным или изменённым токеном отклоняется;
3. запрос с действующим токеном успешно проходит аутентификацию;
4. после истечения срока действия токен перестаёт работать;
5. значение токена, полученное клиентом, отсутствует в базе данных в открытом виде;
6. два успешных входа пользователя создают разные токены.

---

## SR-03. Изоляция данных пользователей

**Требование.**  
Обычный пользователь должен иметь доступ только к собственным данным и операциям.

Пользователь не должен иметь возможность получить баланс, историю списаний или список заказов другого пользователя, а также зарегистрировать или использовать для списания заказ, принадлежащий другому пользователю.

Идентификатор пользователя для пользовательских операций должен определяться на стороне сервера из аутентифицированной сессии, а не приниматься от клиента как доверенное значение.

**Критерий приёмки.**

Создаются два пользователя `A` и `B`.

Для пользователя `A` проверяется, что:

- запрос списка заказов возвращает только заказы `A`;
- запрос баланса возвращает только баланс `A`;
- история списаний содержит только операции `A`;
- попытка загрузить номер заказа, принадлежащий `B`, отклоняется;
- попытка списать бонусы на заказ пользователя `B` отклоняется;
- изменение параметров HTTP-запроса не позволяет указать произвольный `user_id` и получить данные `B`.

Ни одна из этих операций не должна изменять баланс или данные пользователя `B`.

---

## SR-04. Разделение пользовательских и административных полномочий

**Требование.**  
Административные операции должны быть доступны только пользователям с ролью администратора.

Обычный пользователь не должен иметь возможности:

- получать список всех пользователей;
- получать список всех заказов;
- блокировать или разблокировать пользователей;
- получать или экспортировать административную статистику.

Администратор, в свою очередь, не должен использовать административную роль для выполнения пользовательских финансовых операций от собственного имени.

**Критерий приёмки.**

С токеном обычного пользователя запросы к маршрутам `/api/admin/*` отклоняются с ошибкой доступа.

С токеном администратора те же маршруты доступны.

Попытка администратора выполнить пользовательскую операцию списания бонусов через `/api/user/balance/withdraw` отклоняется.

---

## SR-05. Блокировка учётной записи

**Требование.**  
После блокировки пользователя его существующие сессии не должны оставаться действительными, а создание новых сессий должно быть запрещено до разблокировки.

Заказы заблокированного пользователя не должны обрабатываться фоновым процессом начисления бонусов во время блокировки.

После разблокировки пользователь должен пройти повторную аутентификацию.

**Критерий приёмки.**

1. Пользователь выполняет вход и получает действующий токен.
2. Администратор блокирует пользователя.
3. Старый токен перестаёт предоставлять доступ к API.
4. Попытка повторного входа заблокированного пользователя отклоняется.
5. Ожидающий обработки заказ пользователя не получает начисление во время блокировки.
6. После разблокировки старый токен остаётся недействительным.
7. После нового успешного входа пользователь снова получает доступ к разрешённым операциям.

---

## SR-06. Защита от повторного начисления бонусов

**Требование.**  
Один и тот же заказ не должен приводить к начислению бонусов более одного раза независимо от повторных запросов пользователя, повторных запусков фонового обработчика или параллельной обработки.

Номер заказа должен однозначно идентифицировать заказ в системе.

**Критерий приёмки.**

Для одного завершённого заказа:

1. заказ загружается пользователем;
2. после обработки бонусы начисляются один раз;
3. повторная загрузка того же номера заказа не создаёт второй заказ;
4. повторная обработка уже завершённого заказа не увеличивает баланс;
5. при нескольких параллельных попытках обработки итоговое начисление соответствует ровно одному начислению.

Например, для заказа стоимостью `1000.00` рублей при ставке `5%` итоговое начисление должно оставаться `50.00` баллов независимо от числа повторных обработок.

---

## SR-07. Атомарность и целостность списания бонусов

**Требование.**  
Списание бонусов должно выполняться атомарно.

Система не должна позволять:

- списать больше бонусов, чем имеется на текущем балансе;
- получить отрицательный баланс;
- списать бонусы на чужой заказ;
- списать сумму больше стоимости заказа;
- выполнить два разных списания для одного и того же заказа.

Повтор точно такого же уже успешно выполненного запроса не должен повторно уменьшать баланс.

**Критерий приёмки.**

При балансе `50.00`:

- списание `20.00` успешно и оставляет `30.00`;
- попытка списать после этого `40.00` отклоняется и не изменяет баланс;
- запрос с нулевой или отрицательной суммой отклоняется;
- сумма больше стоимости заказа отклоняется;
- списание на чужой заказ отклоняется.

Если два запроса одновременно пытаются списать средства, которых достаточно только для одного запроса, успешно выполняется не более одного списания, а итоговый баланс никогда не становится отрицательным.

Повтор ранее успешного запроса с тем же номером заказа и той же суммой не уменьшает баланс повторно. Запрос для того же заказа с другой суммой отклоняется как конфликт.

---

## SR-08. Проверка данных внешнего Order Service

**Требование.**  
Данные, полученные от внешнего Order Service, не должны автоматически считаться доверенными.

Перед начислением или списанием LoyaltyLedger должен проверить как минимум:

- номер заказа;
- владельца заказа;
- состояние заказа;
- сумму заказа;
- корректность формата ответа.

Начисление допускается только для заказа соответствующего пользователя, находящегося в состоянии, разрешающем начисление.

Списание допускается только для собственного заказа пользователя в допустимом состоянии.

При недоступности внешнего сервиса или получении некорректного ответа система не должна выполнять финансовую операцию на основании непроверенных данных.

**Критерий приёмки.**

Проверяются ответы Order Service со следующими изменениями:

- другой `owner_id`;
- другой номер заказа;
- неизвестное состояние заказа;
- отрицательная сумма;
- отсутствующая сумма;
- некорректный JSON;
- HTTP-ошибка;
- таймаут.

Во всех случаях, когда данные не могут быть достоверно проверены, баланс пользователя не изменяется.

---

## SR-09. Ограничение и валидация входных данных

**Требование.**  
Система должна проверять пользовательские входные данные до выполнения бизнес-операций и ограничивать размер обрабатываемых запросов.

Некорректные данные не должны приводить к изменению состояния системы, панике приложения или выполнению частично завершённой финансовой операции.

В частности должны проверяться:

- формат логина и длина пароля;
- формат номера заказа;
- сумма списания;
- параметры пагинации;
- размер JSON-запросов;
- размер ответов внешнего Order Service.

**Критерий приёмки.**

Система отклоняет:

- слишком короткий или слишком длинный логин;
- логин с пробельными или управляющими символами;
- пароль недопустимой длины;
- некорректный номер заказа;
- отрицательную или нулевую сумму списания;
- неизвестные поля в JSON;
- несколько JSON-объектов в одном запросе;
- запрос, превышающий установленный лимит размера;
- некорректные значения `limit` и `offset`;
- чрезмерно большой или некорректный ответ внешнего Order Service.

После отклонённого запроса состояние баланса, заказов и списаний должно оставаться неизменным.

---

## Критерий выполнения требований в целом

Требования `SR-01`–`SR-09` считаются выполненными, если для каждого требования существует воспроизводимая автоматическая либо ручная проверка, а нарушение проверяемого условия приводит к отказу операции без несанкционированного изменения данных.

В модели угроз каждое приоритетное `T-*` должно быть связано как минимум с одним требованием `SR-*`, а в разделе проектных решений будет указано, какими `D-*` обеспечивается выполнение каждого требования.
